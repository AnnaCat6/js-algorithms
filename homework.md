## Конспекты

### Гит для новичков (часть 1) — мои мысли

- Раньше думала, что коммит — это просто «сохранить», а теперь поняла: это «сохранить состояние всей папки». Как чекпоинт в игре — если что-то сломается, можно откатиться.
- Три зоны Git наконец встали на места: рабочая папка → индекс (stage) → репозиторий. `git add` — это положить в корзину, `git commit` — зафиксировать снимок. Теперь не пытаюсь коммитить всё подряд без подготовки.
- Коммит должен быть атомарным: один коммит = одна логическая мысль. Например, «добавил функцию sum» или «поправил баг». Это сильно помогает потом читать историю.
- `.git` — это база данных всей истории проекта. Не боюсь её видеть: понимаю, что именно там Git хранит все коммиты и связи между ними.
- Главное открытие: GitHub — это не Git. Git живёт у меня на компьютере, а GitHub — просто место, куда отправляю копии коммитов. Значит, можно спокойно коммитить без интернета, а `push` делать позже.
- Первый коммит теперь делаю осознанно: это точка отсчёта, от которой растут все изменения.
- История коммитов (`git log`) — это тоже документация. Если через месяц не пойму, зачем что-то меняла, `git log` подскажет, что и почему я делала.

## Git для новичков (часть 2) — командная работа

- Прямое обновление `main` допустимо только для мелких правок без кода (документация, заметки, опечатки), когда риск минимален.
- Для любого кода всегда используется полный цикл: ветка → PR → код‑ревью → 2 апрува → мерж. Это правило не отменяется.
- `git pull origin main` перед пушем обязателен, чтобы не отправить устаревшую версию ветки.
- Прямой пуш в `main` — это исключение для обучения: важно понимать механику и границы её применения.
- В реальных командах прямой пуш в `main` часто запрещают на уровне настроек репозитория (branch protection rules).
- Даже для заметок важно делать атомарные коммиты с понятными сообщениями, чтобы история была читаемой.
- Если ветка отстаёт, Git не даст сделать `push` и попросит сначала сделать `pull` и решить возможные конфликты.
